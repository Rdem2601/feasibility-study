# ADR-002: Use synchronous database access

- **Status:** Accepted
- **Date:** 2026-10-13

## Context

The backend is a FastAPI application talking to PostgreSQL (see ADR-001).
SQLAlchemy supports both a synchronous API (`Session`, `create_engine`)
and an asynchronous one (`AsyncSession`, `create_async_engine`, with an
async driver such as asyncpg).

The expected load is low: the application is used by a small number of
users, and requests are short (a few SQL queries each). Concurrency is
not a constraint we expect to hit.

## Options considered

### Option A: Asynchronous access (`AsyncSession` + async driver)

Non-blocking database calls, with `async def` endpoints and `await` on
every query.

### Option B: Synchronous access (`Session` + psycopg)

Regular `def` endpoints. FastAPI runs them in a thread pool, so the event
loop is not blocked.

## Decision

We choose **Option B**.

- **Few users:** async brings a benefit when many requests wait on I/O at
  the same time. With our expected number of concurrent users, the
  FastAPI thread pool (40 threads by default) is more than enough.
- **Simplicity:** synchronous code is easier to write, read, debug and
  test. No `await` everywhere, no `async` contamination of helpers.
- **Fewer pitfalls with the ORM:** async SQLAlchemy forbids implicit lazy
  loading and requires explicit eager loading, extra care with session
  lifecycle, and `run_sync` for some operations (e.g. Alembic migrations).
- **Tooling:** the synchronous stack (ORM, Alembic, pgvector and PostGIS
  helpers, scripts, notebooks) is the most widely documented and the
  least surprising.

## Consequences

**Positive**

- Simpler code and a lower learning curve for contributors.
- Easier testing and debugging.

**Negative / accepted trade-offs**

- Each in-flight request holds a thread while waiting on the database.
  Throughput under high concurrency is lower than with async.
- Long-running calls (e.g. to an LLM) should not hold a database session
  open while waiting.

**Revisit if**

- The number of concurrent users grows significantly and we observe
  thread pool or connection pool saturation.
- We add endpoints that spend most of their time waiting on I/O
  (streaming, many parallel external calls). Migration is localized: the
  engine, session dependency in `app/db.py`, and the endpoints that use it.
