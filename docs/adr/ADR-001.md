# ADR-001: Use PostgreSQL with pgvector and PostGIS as the single database

- **Status:** Accepted
- **Date:** 2026-10-06

## Context

The application needs to store and query three kinds of data:

- **Relational data:** documents, their versions, and metadata.
- **Vector embeddings:** chunks of the PDM regulation, for semantic retrieval.
- **Geospatial data:** zoning layers of the PDM, to determine which rules
  apply to a given plot of land.

A typical query combines all three: find the regulation articles that are
semantically relevant to the user's question, restricted to the land-use
categories that intersect the user's plot.

The expected volume is small: a few thousand chunks for the PDM regulation.

## Options considered

### Option A: PostgreSQL + a dedicated vector database (Chroma)

PostgreSQL (with PostGIS) for relational and spatial data, Chroma for embeddings.

### Option B: PostgreSQL only, with the pgvector and PostGIS extensions

A single database handles relational, vector and spatial data.

## Decision

We choose **Option B**.

- **Spatial queries require PostGIS anyway**, so PostgreSQL is needed in
  both options. The real question is whether to add a second database
  for vectors.
- **Combined queries:** spatial filtering, metadata filtering and vector
  similarity can be expressed in a single SQL query. With two databases,
  the application would have to orchestrate several round trips and keep
  a copy of the metadata in Chroma.
- **Consistency:** a chunk's text, metadata and embedding are updated in
  the same transaction. With two databases, there is no shared
  transaction, and a partial failure could leave them out of sync.
- **Scale:** our volume does not justify a specialized vector database.
  pgvector handles a few thousand vectors without difficulty.
- **Operational simplicity:** one service to run, back up and deploy.

## Consequences

**Positive**

- A single source of truth for all data.
- Simpler application code: no synchronization logic between stores.
- Standard SQL tooling (ORM, migrations, backups) applies to vectors too.

**Negative / accepted trade-offs**

- No managed hosting: we run and maintain the database ourselves
  (Docker locally, a hosting choice to make later).
- More complex interface than Chroma's Python API: SQL, an ORM and
  migrations are required.
- Unlike Chroma, pgvector does not create a vector index automatically: we must decide  
  which index type to use and create it explicitly.
- No built-in dashboard to inspect embeddings and collections.
- If the volume grew by several orders of magnitude, a dedicated vector
  database might become worth reconsidering. This would require a new ADR.

## Implementation notes

- Custom Docker image based on `postgis/postgis`, with pgvector installed
  from the PostgreSQL apt repository (see `docker/db/Dockerfile`).
- PostgreSQL 18.
